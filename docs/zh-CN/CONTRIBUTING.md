# 参与贡献

如果你想帮忙翻译模组界面或文档，请看[翻译指南](TRANSLATING.md)。

## 准备工作

不论是修复 bug、完善文档、补充测试、日常维护还是开发新功能，都非常欢迎。

如果你想找点事做，可以看看带有 https://github.com/12src/12pit/labels/confirmed 和 https://github.com/12src/12pit/labels/help%20wanted 标签的未关闭议题；刚接触项目的话，可以从同时带有 https://github.com/12src/12pit/labels/confirmed 和 https://github.com/12src/12pit/labels/good%20first%20issue 标签的议题入手。动手前请先看一下负责人、评论和关联的拉取请求，确认还没有别人接手。

如果改动需要设计新功能，或者会显著影响模组的其他部分，请先提一个议题讨论，具体要求见[议题指南](ISSUES.md)。拿不准改动范围时，可以在议题里问，或者到 [Discord](https://discord.gg/e9PRKMUenc) 的 `#developer` 频道交流。

## 认领议题

开始处理某个议题时，请在议题下留条评论。如果改动可能和其他人的工作有重叠，建议尽早提交一个草稿拉取请求（Draft PR），方便大家了解你在做什么。

## 开发改动

每次提交请专注于一件事，提交说明请使用[约定式提交](https://www.conventionalcommits.org/)格式，比如 `fix: correct profile loading` 或 `docs: clarify build steps`。一个拉取请求通常只解决一个目标，如果几处小改动紧密相关、方便一起审查，也可以合在同一个拉取请求里。

动工前建议先读一下[架构指南](ARCHITECTURE.md)了解包边界和依赖关系，再参考[调试指南](DEBUGGING.md)运行开发客户端和检查。

改代码前先看看相关模块现有的实现，能复用现有工具的尽量复用。新增逻辑放在所属功能的包内，确实有多处复用需求时再提取到共享层，不要在拉取请求里顺手做无关的代码清理。

[BootstrapLayoutTest](../../src/test/java/pit12/BootstrapLayoutTest.java) 会实例化各功能的配置类来检查分类和注册顺序。不需要注入依赖的配置类使用 `public` 无参构造器；如果新增的配置类需要传入构造参数，记得同步更新该测试。

项目里的界面文案、日志和文档请保持自然、简练。

## 编码规范

只写当前功能真正需要的代码，有第二个实现或测试等实际需求时再引入接口或包装类。一段逻辑如果多处用到，或者抽出来确实更易读，再提取成方法、常量或变量；只用一次且内联就很清楚的表达式直接内联。不要保留逻辑重复的方法，也不要写只做简单转发的包装方法。

用户输入、磁盘与网络数据，以及可能为空的 Minecraft 值，统一在进入项目的边界处检查。项目内部调用默认由调用方保证参数有效，不要跨层重复判空或检查范围；内部不变量被破坏属于代码缺陷，应该直接暴露出来。不过 `stop()` 有可能在启动中途失败后执行，释放资源前仍需判断资源是否已创建。

只有把集合交给可能修改它的外部调用方，或者跨线程传递时，才做复制。

实时游戏状态统一在客户端主线程读写，文件读写、HTTP 请求和耗时计算放在组件自己的工作线程里执行。工作线程返回结果后，先检查所属组件是否仍在运行，以及会话、世界或请求代次是否仍然有效，再应用结果。更新状态时，先把内部状态改完再通知监听器，保证回调看到的始终是新状态。

读取文件失败时不要覆盖原有文件；写入失败时保留未保存标记，并在确认保存修订号匹配后再清除标记。修改文件格式时请兼容旧版本，并保持已保存的配置 ID 不变。只在实际能处理或能补充有效上下文时捕获异常，不要写只重抛或吞掉异常的 `catch` 块。

避免每帧解析或全图扫描这类明显的性能浪费，加缓存或特殊分支前先确认实际收益。如果某项优化的收益微乎其微，却让代码复杂很多，优先用简单直接的做法。

及时删掉改动中不再使用的方法、字段、参数、导入和类。删除公开成员前，先在整个仓库（包括测试、文档和 Mixin 配置）里搜索引用。直接使用 Java 的自动装箱和常规 `import`，不要手写装箱调用或全限定类名。

## 注释

站在第一次读这段代码的人的角度想一想：如果第一眼看代码就能明白它在干什么，就不用写注释；如果某处的设计原因、边界条件或外部 API 的特殊行为无法直接从代码看出来，就补一句简短的说明。改代码时记得同步更新相关注释。

## 提交拉取请求

拉取请求标题请用简短的英文，方便直接作为更新日志条目，例如 `Remove gaps between timer groups`。如果包含几处相关联的改动，在标题里概括共同目标，并在描述中列出具体内容。

将拉取请求标记为可审查前，请先运行 `./gradlew spotlessApply` 与 `npm run format --prefix web-ui`，再跑一遍 `./gradlew check` 并完整构建一次。如果修改了行为，请补充对应的测试。在描述中写明改了什么、为什么改，以及实际运行了哪些检查。
